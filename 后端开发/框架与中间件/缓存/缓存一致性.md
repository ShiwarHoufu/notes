# 问题根因

1. 缓存与 DB 是两个独立的系统，没有共同的事务。（更新DB成功，删缓存失败）
2. 全局并发读写没有顺序，导致旧值覆盖新值。
# 操作顺序

从操作顺序来考虑。通常有两种方式：
- 先删缓存，再DB
- 先DB， 再删缓存

为什么“删”缓存，而不去更新缓存：
1. **并发写很容易脏数据**。
2. **无效写**。在写多读少的场景下，更新了缓存之后可能根本没有人读，浪费资源。
## 先删缓存 再更库

![[Pasted image 20261014163636.png|603]]

很明显，当更新操作的两步之间插入了查询操作，就导致了最终缓存和数据库的数据不一致，只能等待缓存过期自动淘汰。

对此，我们可以使用**延迟双删**来应对这个问题。

### 延迟双删

顾名思义，延迟一段时间后再删一次缓存。对于上图，就可以补充为这样：
![[Pasted image 20261014184020.png|583]]

实现延迟最简单的方式就是直接让线程 sleep，同时业务也被阻塞了。显然这样做是不推荐的。
所以，常常使用**MQ**，再**订阅数据库binlog**来实现延迟双删：（常见的订阅工具比如Canal）

1.  Canal 伪装成 MySQL 从库，订阅 binlog；
2.  Canal 收到变更，向MQ投递消息；
3.  消费者收到消息执行执行第二次删除。

延迟双删**适用的场景**：**读多写少**
- 每次写操作都需要删两次缓存，异步任务、投递消息；写的操作多了，系统压力大。

## 先更库 再删缓存

![[Pasted image 20261014140135.png|599]]
这是一个**理想情况**。尽管查询线程第一次返回的是旧数据 ，但还是实现了最终一致性。

在先更库再删缓存这种策略下，存在一个可能性很小的异常场景：
![[Pasted image 20261014141514.png|597]]
最终缓存里存的是1，而数据库中存的是2，不一致。

为什么说这个场景发生的**可能性小**，因为要满足两个要求：
- 缓存不存在
- 查询线程拿到旧DB数据之后，可能发生阻塞，**等很久才写缓存**（等到更新线程执行完删缓存）
>可能性小，不意味着不可能。要处理这个问题，同样可以采用**延迟双删**
