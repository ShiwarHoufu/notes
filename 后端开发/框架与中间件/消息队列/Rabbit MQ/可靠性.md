
## 生产者确认机制

可能发生以下问题：
1. 网络闪断：生产者发送方法返回成功，但消息卡在 TCP 缓冲区，还没传到 MQ，连接断了 → 消息丢了，生产者以为发成功了。
2. Broker 内异常：消息到达 Broker，但是 Broker 磁盘满、持久化失败、内部报错，无法收下消息。

RbbitMQ提供了两个核心机制：**Publisher Confirm、Publisher Return**
1. **消息到达交换机，但是路由不到队列** → confirm ack，同时触发 return 回调。 
2. **临时消息**：送到交换机、成功入队 → confirm ack
3. **持久消息**：送到交换机、入队并且持久化完成 → confirm ack
4. 其余情况： confirm nack

Spring Boot 配置：
```yml
spring:
  rabbitmq:
    publisher-confirm-type: correlated
    publisher-returns: true
    template:
      mandatory: true
```
**publisher-confirm-type:**
- **none**：默认。关闭生产者确认。
- **correlated**：**异步**回调，消息携带 **CorrelationData**，最常用。
- **simple**：支持异步回调，也支持`waitForConfirms()`同步阻塞等待回执。

**！！注意！！**
1. 生产者确认机制需要**额外的网络和系统资源开销**：
	 不开 confirm 的瞬时消息单连接可到 10 万级 msg/s；持久化 + confirm 常见落在几千到一两万 msg/s
2. 一般不会开启 return 机制，因为一般路由失败都是自己的代码问题。

## MQ 可靠性

### 数据持久化

队列中的消息**持久化到磁盘**，MQ重启后消息依然存在。
> 同时开启 生产者确认（confirm）和 持久化 时，RabbitMQ只在消息持久化完成后才返回ack

三层缺一不可：交换机持久化、队列持久化、消息持久化

| 层级  | 开关               | 持久化的是什么         | 没开的后果         |
| --- | ---------------- | --------------- | ------------- |
| 交换机 | `durable=true`   | 交换机元数据 + 绑定关系   | 重启后交换机和绑定一起没  |
| 队列  | `durable=true`   | 队列元数据（名字、参数、绑定） | 重启后队列消失       |
| 消息  | `deliveryMode=2` | 消息体 + 属性        | 消息没了（瞬时消息不落盘） |
## 消费者确认机制

消费者处理完消息后，要向 RabbitMQ 发回执，告知处理结果。
没有回执，MQ 就无从判断消息是否已被消费成功。

| 回执         | 含义         | RabbitMQ 的动作 |
| ---------- | ---------- | ------------ |
| **ack**    | 成功处理消息     | 从队列中删除该消息    |
| **nack**   | 处理失败       | 再次投递消息（重新入队） |
| **reject** | 处理失败并拒绝该消息 | 从队列中删除该消息    |

SpringAMQP 的三种 ACK 处理方式
通过配置 `acknowledge-mode` 选择处理方式：

| 模式         | 行为                                               | 评价          |
| ---------- | ------------------------------------------------ | ----------- |
| **none**   | 不处理。消息投递给消费者后立刻 ack                              | 不建议使用       |
| **manual** | 手动模式。业务代码中自己调用 API 发送 ack / reject               | 存在业务侵入，但更灵活 |
| **auto**   | 自动模式。SpringAMQP 用 **AOP 环绕增强**包裹消息处理逻辑，按执行结果自动回执 | 最常用         |

auto 模式的判断逻辑：
- 业务异常 → 自动返回 **nack**
- 消息处理或校验异常 → 自动返回 **reject**

## 失败消息处理策略

消费者处理失败时，先经由**本地重试**：
```yml
retry:  
  enabled: true  
  # 这一项在 Spring Boot 4 里叫 max-retries，不是老教程里的 max-attempts。  
  max-retries: 3  
  initial-interval: 2s  
  multiplier: 2.0  
  max-interval: 10s
```
重试次数耗尽后，交给 **MessageRecoverer** 决定去向。
**MessageRecoverer** 接口有三种实现：

| 实现                                   | 耗尽后的动作             | 结果               |
| ------------------------------------ | ------------------ | ---------------- |
| **RejectAndDontRequeueRecoverer**    | 返回 **reject**，     | **默认**方式，消息直接丢失  |
| **ImmediateRequeueMessageRecoverer** | 返回 **nack**        | 消息回到队列           |
| **RepublishMessageRecoverer**        | 把失败消息**投递到指定的交换机** | 比如，失败消息转入专门的错误队列 |
