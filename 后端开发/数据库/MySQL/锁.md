锁是 MySQL 用来**解决并发写冲突**的机制，多个事务同时修改同一行数据时，通过锁控制访问权限，保证数据并发访问的**一致性**。

# 一、全局锁

对整个数据库实例加锁，加锁后整个实例处于**只读状态**——后续的 DML 写语句、DDL 语句、以及更新操作的事务提交语句都会被**阻塞**，但 **DQL 不受影响**。

## 1. 应用场景

**全库的备份**。对所有的表进行锁定，从而获取一份**一致性视图**，保证备份数据的完整性。
不加锁逐表备份就会出现**数据不一致**（备份不是瞬间完成的，期间业务仍在写入）
```sql
-- 加全局锁
flush tables with read lock;
```

```bash
# 备份
mysqldump -u用户名 -p 数据库名 > 备份文件.sql
```

```sql
-- 释放
unlock tables;
```
## 2. 特点：一次较重的操作

加全局锁的代价取决于备份在哪台机器上执行：

| 备份位置   | 后果                                          |
| ------ | ------------------------------------------- |
| **主库** | 备份期间不能执行更新，**业务基本停摆**                       |
| **从库** | 备份期间从库无法执行主库同步过来的二进制日志（`binlog`），导致**主从延迟** |

## 3. 替代方案

InnoDB 引擎下，备份时加上 `--single-transaction` 参数，即可完成**不加锁**的一致性数据备份：

```bash
mysqldump --single-transaction -uroot -pxxxx xxxx > xxxx.sql
```

> 同样是拿到一致性视图，这个方式不需要把整个实例置为只读，避开了停摆与主从延迟的代价。


# 二、表级锁

## 表锁
>InnoDB 支持表锁，但默认优先用行锁

1. **表共享读锁（S 锁，READ LOCK）**
2. **表排他写锁（X 锁，WRITE LOCK）**
![[IMG_20261015_091533.jpg|351]]

## 元数据锁（MDL）

MDL（meta data lock） 是 MySQL **Server 层**的表级逻辑锁，在访问一张表时自动加锁，**事务结束才释放**。
作用：保护表的元数据（字段、索引等），**避免 DML 和 DDL 冲突**，保证读写一致性。
![[IMG_20261015_092506.jpg|700]]

## 意向锁

Intention Lock 是**InnoDB 引擎层**的表级锁，配合行锁一起使用。
作用：在给表**加表锁时**，为了避免加的表锁与行锁冲突，会先判断整张表有没有行锁；而为了避免遍历全表所有行去检查锁，就引入了意向锁，可以**快速判断整张表有没有行锁**。

1. **IS 意向共享锁** 事务要给表中某一行**加 S 行锁之前**，先在表上加 IS 意向锁
2. **IX 意向排他锁** 事务要给表中某一行**加 X 行锁之前**，先在表上加 IX 意向锁

>意向锁只和表级 S/X 锁做冲突判断；**意向锁之间互相兼容**

# 三、行级锁

行级锁**每次锁住对应的行数据**，锁定粒度最小、发生锁冲突的概率最低、并发度最高，应用在 **InnoDB 引擎**中。

InnoDB 的行级锁分为三类：

| 行级锁类型             | 锁定范围              | 作用                              | 支持的隔离级别 |
| ----------------- | ----------------- | ------------------------------- | ------- |
| 行锁 Record Lock    | 单个行记录             | 防止其他事务对此行进行 `update` 和 `delete` | RC、RR   |
| 间隙锁 Gap Lock      | 索引记录间隙（**不含**该记录） | 防止其他事务在间隙 `insert`，**解决幻读**     | RR      |
| 临键锁 Next-Key Lock | 行锁 + 数据**前面的**间隙  | 行锁和间隙锁的组合，既锁住数据本身，又锁住这条数据前面的间隙。 | RR      |

## 1. 行锁（Record Lock）

| 当前锁 \ 请求锁 | S（共享锁） | X（排他锁） |
| --- | --- | --- |
| **S（共享锁）** | 兼容 | 冲突 |
| **X（排他锁）** | 冲突 | 冲突 |

| SQL                             | 行锁类型    | 说明                                      |
| ------------------------------- | ------- | --------------------------------------- |
| `INSERT`、`UPDATE`、`DELETE`      | 排他锁     | 自动加锁                                    |
| `SELECT`（正常）                    | **不加锁** |                                         |
| `SELECT ... LOCK IN SHARE MODE` | 共享锁     | 手动加 `LOCK IN SHARE MODE` |
| `SELECT ... FOR UPDATE`         | 排他锁     | 手动加 `FOR UPDATE`         |

## 2. 间隙锁与临键锁

默认情况下，InnoDB 在RR事务隔离级别运行，使用**next-key 锁**进行搜索和索引扫描，**防止幻读**

> 幻读：同一个事务内，两次范围查询，中间别的事务插入了新数据并提交，导致当前事务第二次查询多出了之前没有的行

**加锁范围会随查询条件改变**：
1. 索引上的**等值查询（唯一索引）**：给**不存在**的记录加锁时，优化为**间隙锁**；命中已存在的记录时则优化为**行锁**。
2. 索引上的**等值查询（普通索引）**：向右遍历，最后一个值不满足查询需求时，**退化为间隙锁**。
3. 索引上的**范围查询（唯一索引）**：会访问到**不满足条件的第一个值**为止。

**间隙锁可以共存**，一个事务采用的间隙锁不会阻止另一个事务在同一间隙上采用间隙锁。

> InnoDB 的数据是基于**索引**组织，行锁是通过对**索引上的索引项加锁**来实现的，**不是对记录加的锁**，所以**不通过索引条件检索数据**时，InnoDB 将对表中的**所有记录**加锁，此时**就相当于升级为表锁**

以普通索引上的等值查询为例，走一遍完整流程：
（索引数据：1,3,5,7,9，col 普通索引，SQL `where col=5`）

1. 读取索引记录 `5`，满足 `col=5`
    - 给 5 加**临键锁：(3,5]**
2. 继续向右取下一条索引记录 `7`，`7≠5`，查询终止
    - 读到 7，本来要给 7 加**临键锁：(5,7]**，但这条 7 不是我们要更新的数据；
    - 于是把临键锁**退化**：去掉 7 的 Record 行锁，只保留 Gap 间隙锁`(5,7)`
